Ria Money Transfer

At Ria Money Transfer my main project was to create an end-to-end forecasting pipeline to predict volumes needed for each country and agent up to 7 days in advance. The main goal was to automatize and improve accuracy of an existing manual process. In terms of KPI’s our goal was to reduce surplus capital while also reducing lockout rates, which meant guaranteeing liquidity while minimizing idle capital (basically reducing over and underfunding).
Before starting the technical parts of the project though, I was requested by the CFO of the XE group to present the POC of the project and explain it in depth in order to get the green light for the project implementation. After successfully getting the approval, I had weekly meetings with him and the other stakeholders to give updates on what was going on and update the project with any changes we deemed necessary.
After that, I worked on making the POC code structured and scalable, since it was a typical notebook project. In order to do that, I used OOP to organize the code and made it generalized by creating parameters which executed the pipeline for different samples (currencies/correspondents, accountancy/operational data). I also created a python package with all the functions needed encapsulated there. The first country which we tackled was Mexico, followed by India.
Technically, this was done using python, pandas and scikit-learn, all of which was tracked in a structured github repository. In terms of cloud computing, I worked with the AWS environment where I used mainly S3 to store data, athena to structure all of the outputs and Glue/ECR to deploy the pipeline. Besides creating the pipeline which trained the data daily and also provided the predictions, I also created a structured sql database with the outputs, the performance, data quality monitoring information and general metadata so we could not only analyze the results but understand when we potentially had issues with the data and what kind of issue there was. In this database I also stored the results of different tests I executed with the pipeline. So whenever I wanted to change features or engineering things in general (e.g. test different hyperparameter setups or statistical transformations) these results were stored there as well. Each execution had an id number which could be used to join different type of data that we wanted to check (e.g. MAPE values using a given set of parameters or execution speed of a given test).
After the results were acceptable, the first models were deployed using scheduled AWS Glue jobs + Github Actions + Terraform in order to guarantee a CI/CD process. A big chunk of the DevOps side of this was built by the DevOps team, but with my guidance in terms of the direction the product should go.
After benchmarking different algorithms I ended up using Extreme Random Forests since it was the best performing one. I did structure the code in a way which was pretty seamless to change algorithms though. In terms of metrics and KPI’s I used MAPE and MAE values to understand and compare performance, with the important factor which was adjusting the output values to separate outlier predictions from stable general ones (which I called adjusted MAPE and MAE, respectively). This actually prompted us to test specific models for seasonal events in which the accuracy dropped which ended up adding more performance to the pipeline (e.g. modeling Christmas and weekends separately). In the end, MAPE values were around between 10-15%, but, more importantly, these were always equal to or better than the manual process. In terms of KPI’s, we saw a reduction of 500,000 dollars per day with underfunding for Mexico and a decrease of around 35% in lockout rates, this compared with the manual process. Also, the overall manual process took several hours to generate remittance predictions, in contrast, the pipeline generated predictions in around 4 minutes for each corridor.
To make the data available to stakeholders, I created a quicksight dashboard which was integrated with the S3 bucket of the project and updated daily after each execution.
Besides all the work I did in my Machine Learning project, since this was the first forecasting project to be deployed, I helped other data scientists understand the process and tweak their own environments to be able to do the same. I also helped data engineering in tracking issues with the data and MLOps to build the best infrastructure to deploy the models. I also did tests on my own using Docker and AWS ECR to prospect different deployment approaches since there was still a lot to be achieved in scalability as the project grew.




Melhor Envio

Melhor Envio is an online platform which estimates best shipping company prices to small and medium sized businesses dynamically. At Melhor Envio, my role as a data scientist was to help stakeholders understand customer profiles, behavior and enhance KPI metrics by using statistically based techniques.  
My first project there was to understand if the churn metric they had (90 days) made any sense, since it was created arbitrarily. In order to achieve that, I quantified the longest periods of time each client spent without using the platform but eventually returning to it, once that was done I ran a bootstrap analysis with these values to create a normal curve which peak would represent approximately what could be expected as a non-churn/churn period. The result of this analysis was that 45 days (the peak of the curve) meant a more reasonable number. As that project evolved, I understood that the behavioral patterns of different clients of the sample was highly heterogeneous and that, although a single number could help direct business efforts, it was a very generalistic approach. As such, I proposed the creation of a new client specific metric based on each client’s behavior, which was coined relative churn. In order to do so, I quantified the frequency in which each active client used the platform and used that number as a baseline to alert to a possible churn. 
As I collected this data and analyzed it, I started creating a real time data pipeline that summarised the statistical behavioral data from each client, showing if the client was behaving as expected, losing activity and if the business should take any action. This was a highly regarded data source to the business and, as such, became a project of its own, which was coined activity status and delivered directly to the board of directors. A key finding in this project was that we were able to detect statistical signals that showed a pattern of decline in activities for the clients way before they abandoned the platform, which meant the company could act to enhance retention and recovery. This was coupled with the company’s marketing team to create alerts and contact clients which represented potential churns. This project became a real time database (called customer activity status database) which showed the patterns and had flags linked to the clients for which we should keep an eye on or contact. I also created a pipeline to plot each client activity through its lifetime, showing the boundaries of a potential churn and absolute churn, to help visualize what the numbers showed.
In parallel, I led the creation of a segmentation model which was a request from marketing to trace personas to different samples of the client base. My goal was to suggest the methodology to be used and guide the team to making it make sense, by basically choosing the right tool and features for the job. In order to do that, I suggested using the K-prototype algorithm since we had mixed data, of which several were categorical. This project was a success and very well received by across different departments of the company. With its results, the business was able to understand the profiles of each group of customers and take assertive business decisions, besides gaining knowledge of aspects unknown before. As an example, the company relied a lot on shipping coupons to provide specific discounts, but they had a relatively low usage since the customer profiles that should use them could be relatively niche. With the model, the company was able to direct coupons to specific groups of customers instead of sending them to the majority of them (or to a random assortment). This resulted in a higher usage rate. Also, by using our model key customers with high ticket values could be easily tracked to get specific offers.
Finally, after the execution and implementation of these projects I was tasked with the development of a machine learning model to predict client churn. This was a classification model (logistic regression) that, besides using available raw data, also used the results of my previous projects as features. At the time of my departure from the company, the AUC for this model was around 0.75, but I left the company before the project was concluded.
During this time, I also was responsible for creating dashboards to attend different team needs. This was done using Looker and LookML.
In terms of stack, most of my work was done using R, which was connected to vscode and the company’s data warehouse via Red Shift. In order to build views and dashboards, I learned to develop dashboards using Looker and the LookML language. Not all KPI’s and ROI metrics were easy to quantify in this case since some (as client base knowledge) were subjective. Of the ones which we could quantify was the fact that at least 70 customers were recovered from churn based on the activity status database, an increase in 20% in responded calls and an increase 30% conversion of coupons for specific test cases. Also, the system created to deal with key accounts was mostly created based on the customer segmentation model. 

PicPay

Picpay is one of the largest Brazilian fintech startups. At PicPay, I was hired in a role which was a bit different from the typical data scientist/analyst roles. I was hired as a Senior Data Analyst with the goal of bridging the gap between analysts (which lacked in software engineering skills) and data scientists (which lacked in statistical knowledge), so I was something of a mixed breed. 
My first project was to help redesign the outdated customer segmentation model which was implemented by the company. It lacked explainability and statistical rigor, besides having doubtful experimental design choices. That was delivered in the form of a new model which used Gaussian Mixture Models and had structured and stable client cluster profiles, with descriptive statistics, hypothesis testing and feature engineering being used to validate/invalidate previous model assumptions.
Afterwards I was asked to help the treasury team build a pipeline to gather several data needed to create a report for the Brazilian Central Bank audit. They needed someone who could learn spark syntax fast and lead the data analysts in creating a pyspark pipeline to gather the data they knew was needed. That was a successful Ad Hoc project which was delivered in three weeks.
Eventually I was allocated to the home page user experience squad, whose mission was to reformat PicPay’s home page app by proposing changes to make it simpler and less cluttered without losing client engagement and also understanding how different customer profiles used it. These were done in two ways. For the former, we removed sections and elements from the home page which we deemed unnecessary and tested the impact of those changes using A/B testing. For the latter, we used the results from different segmentation models in the company coupled with the home page metrics and data to understand how its usage differed among profiles. After these were done we also used the Multi Armed Bandit algorithm to propose recommendations to different customer profiles in the home page.

Carrefour

Carrefour is the largest retailer in South America. At Carrefour I was responsible for developing an end-to-end modeling project to create a deployed forecasting model to predict sales for promotional events, focused on fast moving consumer goods, 21 days in advance besides aiding its integration with the company’s ERP tool.
In order to achieve that I firstly led the creation of a clean orchestrated ETL pipeline to make all regarding product sales available to the supply team. Once that was done I developed a machine learning model using lgbm and good experiment design practices to generate reliable forecasts. Afterwards, I joined forces with the Machine Learning Operations team to deploy a parallelized pipeline which predicted sales for future events every day using Vertex AI and Kubeflow Pipelines, besides optimizing the code to do so. Code was optimized by translating pandas code to polars and tweaking overall code (using modularization and vectorization for example). Each store had its own sales model which were trained daily in parallel. Code optimization reduced a process that took 6 hours to 40 minutes.
Once that was done I created the experimental design to test the efficiency of our model, by using hypothesis testing and comparing sales and stock numbers to the baselines (e.g. stores not using our model and past stock surplus averages). I also created the performance database of the model which allowed us to track bugs and performance.
At Carrefour I worked closely with stakeholders and upper management (data directory) to ensure transparency, help with data literacy and explain results with statistical robustness. I helped, for example, the stakeholders understand the issues with outliers and mape values, besides exploring which products were having accurate forecasts and which were not. I used mainly MAPE and wMAPE values, with proper statistical adjustments for all these.
I also created product specific models which performed better than using single models per store. Since the project was a success, the company asked for me to conceive a model to predict regular sales as well.
